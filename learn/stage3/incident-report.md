## 二、排查路径（按你实际的顺序，每步：敲了什么 → 看到什么 → 由此推出什么）

<!-- 例如：先看了什么？为什么先看它？线索把你引到哪里？允许写"这一步走了弯路"——复盘里弯路比正确更值钱。 -->

1. 先看到了写着api返回502，这是部署结果，展示出来的

2. 这个时候去服务器上面看一下各个服务是否正常docker compose -f docker-compose.prod.yml --env-file .env.prod ps，显示DB_PASSWORD这个值还未设置，通过打印日志看，docker logs prompt-studio-app --tail 30，结果显示authentication，猜测到时密码错误、或者根本没配置。

3.去配置文件.env.prod文件上配置上这个值，并思考这个值应该是与POSTGRES_PASSWORD的值一致。然后重启服务，进行空提交，runner捕获到这个单子，进行重新部署。
4、重新部署时发现 runner 是 Offline 的、单子没人领——>用 systemctl status + journalctl 验尸，看到"token expired / registration deleted"（昨晚 Mac 睡眠、VM 挂起太久，注册过期了，服务不再重试）→ sudo ./svc.sh start 把它拉起来 → 积压的单子被自动领走（单子没丢）。
5、runner 领了单却跑了 3 分 13 秒就 Failed → 上 GitHub 页面点开步骤日志，点开是空白（上传日志的请求也失败了）→ 换到 VM 上翻 _diag/blocks/ 里的本地日志副本 → 看到构建死在“解析 node:22-alpine 元数据”，daemon.json 里配的两个加速器域名已 NXDOMAIN → 改用不带 --build 的 docker compose up -d（修复只是环境变量，不需要重建镜像，绕开仓库依赖）→ 网站复活。

## 三、根因（一条因果链，从"谁的提交"到"网站挂了"）

<!-- 用箭头串：某变量 → 某结果 → 某结果 → … → app 容器崩溃。根因要能一句话说给产品经理听。 -->

DB_PASSWORD变量未设置
->提交把 compose 里 app 的数据库密码变量改名为 DB_PASSWORD
→ .env.prod 里没有这个新名字
→ compose 不报错，把缺失变量悄悄插值成空字符串
→ 连接串密码为空 → PostgreSQL 认证失败（P1000）
→ migrate deploy 失败 → 容器退出 → restart 策略反复拉起反复死
→ caddy 背后无人 → API 502

## 五、以后怎么防（至少两条，写成团队规约的口吻）

<!-- 例如：这类事故在哪个环节本可以被拦住？（部署后健康检查？变量改名清单？）提示：本次 Actions 是绿勾，但网站挂了——这个矛盾本身就值得一条规约。 -->

1. 不要随便改生产配置文件，改了之后，需要校验更改的值是否正常

2. 改了文件后，需要重新部署后，校验是否正常。即自测

3.部署流水线绿勾不代表应用健康（app 没配 healthcheck，compose 只等启动不等健康）——部署后必须做健康探测（给 app 配 healthcheck，或流水线最后一步自动 curl 探针），绿勾不作为上线依据；

4.给配置变量改名时，必须 grep 全仓库确认所有引用点并同步修改（本次就是只改了 compose、没同步改 .env.prod 造成的）。   

## 六、本次事故教你的三句话（费曼压缩，给未来的自己）
绿勾不等于健康；本地有镜像不代表不用问仓库；应急修复能绕开构建就绕开。
